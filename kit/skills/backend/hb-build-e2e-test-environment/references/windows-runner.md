# Running the environment from Windows

**Opt-in. Read this only when Windows-native scripts have actually been asked for.** The default is
Ubuntu or WSL2, the `.sh` set is canonical, and nothing here is needed to build the environment.
Referenced from the machine assumptions in [SKILL.md](../SKILL.md).

## Why there is a default at all

Carrying two script sets means every change has to be made twice, and one of them eventually is not.
The way that fails is *"the environment comes up ninety percent of the way, but only on Windows"* —
precisely the failure this skill exists to prevent. So the second set is written only when someone
has decided they need it, and the cost is carried by whoever decided.

**Look for a way to avoid it first.** Everything moved into a container is a thing that stops
differing per OS. `docker compose` behaves identically everywhere; only the host-side driver does
not. A stack in shape A — client, edge and application all containers ([edge-and-proxy.md](./edge-and-proxy.md))
— needs almost no host-side scripting at all, and that is the real fix.

## What differs per machine

| | Linux / WSL2 | macOS | Plain Windows |
| --- | --- | --- | --- |
| bash | 4 or later | **3.2** — no `declare -A`, `mapfile`, `${x,,}` | none |
| core utilities | GNU | **BSD** — `sed -i` needs an argument; no `timeout`, `date -d`, `grep -P` | none |
| memory ceiling | the machine's | the Docker VM's allocation | the WSL2 VM's allocation, **half the machine by default** |
| bind-mount speed | native | slower, over VirtioFS | very slow under `/mnt/c` — keep the repository on the Linux side |
| line endings | LF | LF | CRLF creeps in via `core.autocrlf` |
| `/etc/hosts` | persistent | persistent | regenerated by WSL2 by default |

The macOS column is why the scripts are written to bash 3.2 with no GNU-only options even though
nobody develops on 3.2 deliberately.

## Why plain Windows does not run the `.sh` set

**What fails is the host-side driver, not the stack.** Everything compose starts behaves the same on
every OS. The five scripts — `up` / `start` / `seed` / `clean` / `down` — are what do not run.

| Depends on | Used for | On plain Windows |
| --- | --- | --- |
| shell language | `set -euo pipefail`, `trap ... EXIT`, `[[ ]]` | no bash; PowerShell has near-equivalents, so this is a rewrite rather than a port |
| background start and PID capture | starting the application and daemons, recording PIDs, stopping them in `down.sh` | `Start-Process` / `Stop-Process` work, but **Windows has no SIGTERM** — only a forced kill |
| `trap ... EXIT` | making sure a failed build leaves no half-stack | `try/finally` is close, but not as complete as `EXIT` |
| host commands | `curl` for health waits, `grep` / `sed` / `awk` for log handling | `curl.exe` exists; `wget` is an alias for `Invoke-WebRequest` with different arguments; the rest are absent |
| file modes | config permissions, the executable bit | NTFS has neither; `chmod` does nothing |
| line endings | scripts, and configs mounted into containers | CRLF surfaces inside the container as `bash\r: bad interpreter` |

**The second row is the one that does not rewrite away.** The design that `down.sh` stops the
processes before the containers assumes a graceful stop. Where only a forced kill is available, a
worker dies holding its connections, and the intent of that ordering is not met. Say so rather than
letting it look equivalent.

**Git Bash mostly works, and fails quietly.** MSYS path translation rewrites arguments on their way
to `docker` (suppress with `MSYS_NO_PATHCONV=1`), and processes and signals are still Windows'.
Worth knowing about; not a configuration to support.

## Requirements, if the set is written

- **PowerShell 7 or later.** Windows PowerShell 5.1 differs in `Invoke-WebRequest` behaviour and in
  error handling, and is out of scope. Say so at the top of each script.
- **The operator's contract does not change.** `up.ps1` / `start.ps1` / `seed.ps1` / `clean.ps1` /
  `down.ps1`, with the same names, the same intentions and the same hand-over output as the `.sh`
  set. One intention, one command — the same rule, on a different OS.
- **`.sh` stays canonical.** A new step is added to the `.sh` set, and reflected in the `.ps1` set
  **in the same change**. Never one alone.
- **Differences that cannot be bridged are written down**, at the top of the script and in its
  hand-over output. Never let it behave differently in silence.
- **Nothing unverified ships.** Record the Windows build and the PowerShell version it was actually
  run on. A script nobody has run is not a deliverable — the same rule as checking from the side
  that consumes it.

## Intention by intention

| Intention | POSIX (canonical) | PowerShell 7 |
| --- | --- | --- |
| stop on first failure | `set -e` | `$ErrorActionPreference = 'Stop'`, plus checking `$LASTEXITCODE` after **every** native command |
| fail on a failure inside a pipe | `set -o pipefail` | **no equivalent** — split the pipeline into stages and check `$LASTEXITCODE` at each |
| cleanup on abort | `trap ... EXIT` | `try { } finally { }` |
| background start, capture PID | `cmd >log 2>&1 & echo $!` | `Start-Process -PassThru -RedirectStandardOutput -RedirectStandardError`, then `$p.Id`. **Both streams cannot target one file**, so keep two logs per process |
| stop a process | `kill` (SIGTERM) | `Stop-Process` (forced). For a graceful stop, give the application its own shutdown signal — a file, an endpoint, a queue message |
| wait for health | `curl` in a loop | `Invoke-WebRequest -UseBasicParsing` in a loop, with connection failures caught by `try/catch` |
| measure a deadline | elapsed seconds | `[Diagnostics.Stopwatch]` |
| locate the script | path relative to the script | `$PSScriptRoot` |

## The shape of one script

```powershell
#Requires -Version 7.0
# Canonical version: start.sh. Change both in the same commit.
# Difference that cannot be bridged: stop is a forced kill — Windows has no SIGTERM.

$ErrorActionPreference = 'Stop'
Set-StrictMode -Version Latest

$root = Split-Path -Parent $PSScriptRoot
$logs = Join-Path $PSScriptRoot 'logs'
New-Item -ItemType Directory -Force -Path $logs | Out-Null

try {
  docker compose -f (Join-Path $PSScriptRoot 'docker/compose.yaml') up -d
  if ($LASTEXITCODE -ne 0) { throw 'compose up failed' }

  # health wait, polled from the host — the side that will use the service
  $deadline = [Diagnostics.Stopwatch]::StartNew()
  while ($true) {
    try {
      Invoke-WebRequest -UseBasicParsing 'http://127.0.0.1:18080/healthz' | Out-Null
      break
    } catch {
      if ($deadline.Elapsed.TotalSeconds -gt 120) {
        throw 'the edge never became reachable. docker compose logs edge'
      }
      Start-Sleep -Seconds 2
    }
  }

  $app = Start-Process -PassThru -FilePath 'node' -ArgumentList 'server/index.js' `
    -RedirectStandardOutput (Join-Path $logs 'app.out.log') `
    -RedirectStandardError  (Join-Path $logs 'app.err.log')
  $app.Id | Set-Content (Join-Path $logs 'app.pid')
}
catch {
  & (Join-Path $PSScriptRoot 'down.ps1')   # never clean.ps1
  throw
}

Write-Host "open http://127.0.0.1:18080/  |  logs: e2e/logs  |  stop: e2e/down.ps1"
```

Note the two log files for one process, the deadline measured with a stopwatch, the health poll made
from the host, and the abort path calling `down`, never `clean` — the same rules as the `.sh` set.

## Recording what was verified

Keep this beside the scripts and update it whenever they change:

```
Verified on: Windows 11 23H2 / PowerShell 7.4.6 / Docker Desktop 29.5.2
Date:        2026-08-22
Scope:       up / start / seed / clean / down, full rebuild from nothing
Not covered: graceful shutdown — Stop-Process is a forced kill
```

An entry that names no version and no date is not a record. If nobody can say which build it ran on,
it has not been verified.
